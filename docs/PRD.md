# 吃什么 APP 轻量版产品需求文档 V0.2

版本：V0.2 轻量版需求基线  
日期：2026年10月7日  
产品暂名：吃什么

一款以照片为主的个人饮食记录 APP。用户轻松记下一餐，回看最近三天、一周、一个月吃过什么，从中决定今天想吃什么。

本版替代 V0.1 的产品定位与首版范围。核心是记录和回顾；AI 识别、营养分析、餐馆推荐、同事投票均为可选扩展，不再是首版交付前提。旧版“不得移出首版”的相关要求撤回。

## 1 产品出发点

用户经常想不起最近吃过什么，纠结时也缺少直观的参考。食物照片能够留下容易回忆的线索，按时间整理后，还能帮助用户发现重复、回想喜欢的餐食。

核心流程：拍照记一餐 → 回看饮食历史 → 自己决定今天吃什么。

例如，看见最近三天吃了两次面，今天想换个口味；翻到上周的某顿饭，又想再吃一次。首版通过方便回看来辅助选择，不要求系统自动分析或给出推荐答案。

首期围绕个人日常饮食使用，可以记录早午晚餐、加餐或其他餐次，不限定公司午餐，不需要同事加入后才有价值。

## 2 首版范围

| 必做能力 | 首版要求 |
| --- | --- |
| 记一餐 | 拍照或从相册选图，快速保存 |
| 看历史 | 按日期展示照片记录，切换最近三天 一周 一个月 |
| 看详情 | 查看大图 日期及已填写的文字 |
| 管理记录 | 补记 修改 删除 |

菜名、餐馆名称、餐次和备注均为可选信息，不能作为保存照片的前置要求。首版每条记录支持一张照片即可；为无图补记或权限受限的场景保留简单文字记录，照片与描述至少填写一项。

首版不要求用户建立餐馆池、填写预算和距离、配置口味档案、连续打卡或注册账户后才能体验。

AI 识别、营养分析、自动选餐、附近餐馆搜索、投票、云端同步、公开社区、商家入驻、支付和配送不纳入本次首版验收。它们不需要在首版界面中占据空入口，也不要求提前建设配套架构。

## 3 页面与使用流程

只需三个主要界面：记录首页、添加或编辑页、记录详情页。新增记录可以使用弹层或页面，不限定导航框架，也不要求为每个动作建立独立标签页。

### 3.1 记录首页

首页就是照片时间线，以“最近吃了什么”为中心。默认查看最近一周，顶部可以切换最近三天、最近一周、最近一个月；新增一餐的入口应明显且随手可达。

记录按就餐日期分组，同日按就餐时间倒序。卡片显示照片、日期或时间，以及用户已填写的菜名或简短描述；餐馆信息有填写时再展示。文字记录使用简洁的文字卡片，不补造食物图片。

首版将三个筛选明确实现为含今天在内的最近 3、7、30 个本地自然日；最近一个月按近 30 天处理，不按日历月。筛选只改变显示范围，不删除更早的记录；提供“全部记录”入口保留长期回看能力。

没有记录时显示“还没有记录，记下这一餐吧”；某个时间范围没有记录时，可新增或查看全部。未记录不能解释为没有吃饭。

不需要首页推荐卡、热量仪表盘或健康评分。照片大小、日期层级和浏览流畅度优先于装饰性元素。

### 3.2 记一餐

用户点击新增，选择拍照或相册，预览照片后即可保存。就餐时间默认当前时间，允许修改为过去时间；餐次可选。

可选字段包括“吃了什么”“餐馆名称”“备注”。餐馆名称首版作为自由文本即可，不要求绑定地点、搜索商家或填写地址。

用户取消拍照或选图时返回编辑状态，不自动生成空记录。保存失败保留已填写内容并允许重试；重复点击保存不能产生重复记录。保存成功后回到首页，相应日期可以找到记录。

首版建议把常见的照片记录操作控制在约 10 至 20 秒内，作为小范围体验观察目标，而非已验证的性能承诺。

### 3.3 详情与管理

点击卡片查看大图和已填写内容，支持修改照片、就餐时间及文字。修改就餐日期后，记录进入正确的日期分组与筛选范围。

支持补记过去的一餐，同一餐次可以有多条独立记录，不以“日期加餐次”强行去重。

删除前进行一次简短确认，删除后该记录不再出现在首页、详情或其他历史范围中。不要增加复杂相册编辑、社交分享或收藏系统作为本轮依赖。

## 4 今天吃什么如何体现

首版把饮食历史作为选择参考。用户先翻看最近的照片，避免无意识地反复吃相同内容，也可以从以前的记录里找到想再吃的餐食。

这部分不需要独立的推荐页面，也不要求计算重复分数、菜系权重或营养缺口。无需为了证明“智能”而引入模型调用。

如果后续使用反馈表明用户需要更主动的帮助，再加入“从我的历史里挑一餐”或简短的饮食回顾。这些属于新迭代，不能自动变成本次必做。

## 5 数据与保存方式

首版默认先做本地保存。用户口中的“拍照上传”在本阶段对应把照片保存成 APP 内的餐食记录；按钮使用“保存”，界面明确记录保存在当前设备，不宣称已经云端备份。

卸载 APP、清除应用数据或更换设备可能导致本地记录丢失，这一限制应在简短的存储说明中告知。云端备份、账号和跨设备同步作为后续需求独立评估。

| 数据 | 最小要求 |
| --- | --- |
| 记录标识 | 稳定 ID 用于编辑 删除及防重复保存 |
| 就餐时间 | 默认当前时间 可修改 用于分组和筛选 |
| 照片 | 可选的本地持久文件引用 |
| 描述与餐馆 | 可选自由文本 |
| 餐次与备注 | 可选 |
| 创建与修改时间 | 支持记录维护 |

照片必须保存到 APP 可持续读取的位置，不能仅引用相机或选图过程的临时文件；关闭并重开后，图片与文字都应存在。数据库记录和文件保存须处理失败情况，避免出现“保存成功但没有图片”。

照片使用适合移动端的尺寸和压缩方式，列表按需加载缩略图，避免每次浏览都读取所有原图。具体参数由实现决定，不新增复杂图片服务。

只在用户拍照或选择图片时请求必要权限；拒绝后提供可行的替代入口或文字记录，不申请定位。照片默认私有，不自动上传第三方分析。

沿用已有合理的移动端技术选型和持久化实现，不因本次需求收敛重建工程。若现有代码已经具备后端或其他功能，先评估可复用部分，不以本 PRD 为理由擅自删除代码、清库或丢弃用户数据。

## 6 首版验收

验收对象是能实际使用的手机 APP。产品范围简化，照片保存与历史查看仍需真实实现。

| 编号 | 验收场景 | 通过标准 |
| --- | --- | --- |
| L01 | 拍照保存 | 只选照片也能保存 不强制填菜名或餐馆 |
| L02 | 相册与文字记录 | 可以选图保存 也可以无图填写描述保存 空记录不允许保存 |
| L03 | 权限拒绝与取消 | 不崩溃 不生成空记录 仍能使用现有历史和文字记录 |
| L04 | 关闭后重开 | 已保存的文字与照片仍能正常显示 |
| L05 | 时间筛选 | 最近 3 7 30 天含今天且边界正确 更早记录仍可通过全部记录查看 |
| L06 | 补记与修改 | 时间 内容和照片的变化正确反映在列表与详情中 |
| L07 | 删除 | 删除后各处均不再显示该记录 关联本地图片按引用关系清理 |
| L08 | 失败与重复点击 | 保存失败不显示成功 输入可继续编辑 重试和重复点击不产生重复记录 |
| L09 | 无网络使用 | 已获取照片后 无网络仍可保存本地记录 查看历史和编辑删除 |
| L10 | 核心体验 | 能完成记一餐 回看三个时间范围 查看旧餐食并自行决定今天吃什么 |

照片拍摄能力需在真机验证；模拟器能验证的路径分别记录。若采用双端目标，两端分别记录验证结果，不能用单端通过推定双端通过。

必要测试聚焦日期筛选边界、记录增删改、重复保存和失败处理，以及真实设备上的图片持久化和重启恢复。测试与实现状态按事实记录，不以静态页面、模拟存储或浏览器预览代替移动端验收。

体验观察只问三个问题：愿不愿意顺手记一餐；能不能快速找到过去吃过的东西；回看是否帮助今天的选择。暂不建设完整埋点平台或设定复杂增长指标。

## 7 开发顺序与交付

第一步完成记录：能拍照或选图、填写可选文字、真实保存并重启恢复。

第二步完成回顾：照片时间线、三个时间范围、全部记录、详情与编辑删除。

第三步完成体验验收：修复权限、空数据、失败、重复提交及弱网问题，验证目标设备，整理启动和试用方式。

这三个步骤构成一个轻量首版。每一步做出可运行结果，常规实现继续推进，不因尚未选择 AI 服务商、地图服务商或部署环境暂停。

交付包含可运行代码、简洁启动说明、实际验证结果和未完成项。必要验证通过后，按项目现有 Git 授权提交、推送开发分支并经 PR 合并；遵守必需检查和审核，不将提交、合并或部署混为一谈。具体环境、分支及代码进度由 Codex 检查当前仓库确认。

## 8 后续扩展

| 扩展方向 | 围绕核心增加的价值 | 启动条件 |
| --- | --- | --- |
| AI 识别菜名 | 减少手动输入 用户可以纠正 | 记录操作确有输入负担 |
| 饮食总结与营养估算 | 帮助理解已记录的餐食 | 有可用数据与明确估算边界 |
| 今天吃什么建议 | 基于个人历史给少量方向 | 用户需要主动建议 |
| 餐馆推荐 | 将想吃的东西对应到可去的店 | 有真实地点数据和场景需求 |
| 同事投票 | 在个人选择之外协助多人协调 | 用户确有共同决策需求 |
| 云端备份 | 减少换机或设备丢失造成的记录损失 | 用户希望保留长期记录 |

商家入驻属于更远期设想，不影响本版交付。扩展项需按实际反馈单独确定优先级，不能因为已写入列表就默认全部实现。

本版的成功标准是：用户愿意把每天的一餐留下来，并能通过这些照片更方便地回顾和选择。
