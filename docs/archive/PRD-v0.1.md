版本：V0.1 产品讨论稿\
日期：2026年10月7日\
产品暂名：吃什么\
适用阶段：需求验证与 MVP 设计

建议将产品定位为工作日午餐决策助手：结合预算、距离、口味和最近吃过的内容，给出少量可执行的餐馆与点餐建议，并让同事快速达成一致。饭后用照片或简单文字完成记录，让下一次推荐更合适。

首版的核心价值是减少选餐时间与重复就餐。饮食记录为推荐提供依据，营养估算作为辅助反馈。商家入驻、交易与配送放到后续阶段。

本文中的版本范围、人数、指标阈值与交互参数均为初始设计建议，需通过试点验证；不是已经验证的市场结论或已承诺排期。

## 1 背景与问题

已知需求来自同事结伴外出吃午饭：每天反复讨论吃什么，最后仍集中在少数几家店。用户希望拍照记录餐食及餐馆，了解大致营养情况，并获得结合过去饮食的推荐。

问题包含三个相互关联的部分：

- 决策负担：候选太多、意见分散，缺少一个能够收敛选择的机制。

- 信息断层：不记得最近吃过什么、哪家值得再去，旧记录没有参与下一次选择。

- 饮食反馈不足：想吃得更多样，但不愿每天称重、查表或填写复杂表单。

核心用户任务：在有限午休时间内，快速找到附近、可接受、最近没吃腻的一顿饭。

需要验证的假设：用户愿意为了更好的推荐完成轻量记录；近期饮食信息确实比纯随机或常去店列表更有帮助；同事能够接受通过链接参与简单投票。

## 2 用户与产品边界

首期建议以一个办公片区的成年上班族为试点，优先覆盖工作日外出午餐，兼容独自用餐与 2 至 6 人同行。城市、客户端平台与团队规模暂未确定。

| 用户 | 主要需求 | 首版对应能力 |
| - | - | - |
| 经常组织午饭的人 | 少提问、快速定店 | 三个候选、一键分享、确定结果 |
| 同行同事 | 表达预算、忌口与今天不想吃的东西 | 简单约束与轻量投票 |
| 希望改善饮食习惯的人 | 看见重复与结构变化 | 餐食记录、食物类别回顾、估算信息 |

产品承诺是“帮你更快选好这一餐，并记住你吃过什么”。首版不承担疾病饮食管理、营养缺乏诊断、专业减重处方或过敏安全认证。

首版暂不包含公开探店社区、商家后台、优惠券交易、外卖配送、复杂好友关系、连续签到惩罚、积分商城及全面维生素追踪。

## 3 产品目标与版本范围

| 能力 | MVP 范围 | 后续扩展 |
| - | - | - |
| 今日吃什么 | 按条件给出最多三个真实候选，支持换一组和帮我选 | 更丰富的个性化与场景 |
| 餐馆池 | 常去店、收藏店、手动添加，具备条件时接入授权地点数据 | 更大范围的新店发现 |
| 饮食记录 | 拍照或文字、餐馆、餐次、日期、简单反馈 | 多餐自动整理与导入 |
| AI 辅助 | 识别菜品候选、用户纠正、有限的营养估算 | 更多菜式和份量辅助 |
| 近期回顾 | 最近七天已记录餐食与重复情况 | 月报与长期习惯分析 |
| 同事决策 | 临时链接、候选投票、发起人确认 | 固定饭搭子与群体偏好 |
| 商业能力 | 仅记录需求，不接入交易 | 商家认领、菜单、合作导流 |

P0 表示完成核心闭环必需；P1 表示核心体验稳定后扩展。AI 可用性不足时，P0 的选餐、手动记录和投票仍须可用，不以 AI 服务成功作为保存记录的前提。

## 4 核心流程与页面

个人流程：打开首页 → 确认本次预算与距离 → 查看最多三个候选 → 选定餐馆 → 出发用餐 → 拍照或快捷记录 → 次日推荐参考已确认记录。

同事流程：发起午饭 → 收集本次约束 → 生成候选并分享 → 同事投票 → 发起人确认 → 各自选择是否记录实际用餐。

| 页面 | 核心内容与操作 |
| - | - |
| 今天吃什么 | 当前条件、三个候选、推荐原因、换一组、帮我选、一起吃 |
| 餐馆详情 | 店名与地址、来源与更新时间、价格范围、个人历史、导航 |
| 记一餐 | 照片或文字、餐馆、菜品、份量可选、确认与保存 |
| 饮食日历 | 已记录餐次、记录详情、修改删除、七天回顾 |
| 午饭投票 | 候选、截止时间、投票状态、最终结果 |
| 我的 | 偏好、常用地点、收藏、不再推荐、隐私与通知设置 |

首页首先回答“今天去哪里吃”，不以热量仪表盘作为默认首屏。不要求用户先完成多天打卡、填写体重或邀请同事后才能得到第一次推荐。

## 5 首次使用与偏好设置

P0 首次使用只收集必要信息：手动选择就餐区域或主动授予定位、设置可接受预算与最大距离、填写明确不吃的食物或口味。预算可跳过；定位拒绝后仍能手动选择区域。

引导用户加入至少三家常去餐馆。少于三家时按实际数量展示，不造出店铺补齐数量。用户没有餐馆且地点服务不可用时，先给出菜系方向，并明确提示补充餐馆；菜系方向不能冒充附近可到达的具体店铺。

偏好区分长期设置与本次设置。长期偏好包括不吃的食物、常用地点、收藏；本次设置包括今天预算、同行人数、可用时间、想尝鲜或想吃熟悉的。偏好改变后立即用于下一次推荐。

“今天不想吃”只影响当天，“不再推荐”长期生效且可撤回。过敏信息属于单独的限制项，不能通过预算调整、换一组或随机选择自动取消。

## 6 推荐与餐馆管理

### 6.1 推荐单元

默认推荐“餐馆加点餐方向”，而非孤立的菜名。例如某餐馆配上“有明确菜单信息时可选的蔬菜和蛋白质组合”。只有菜系资料时，不虚构具体菜名、价格、库存或单份热量。

每张候选卡显示店名、可用的距离信息、预算匹配情况、一至两条真实推荐原因、最近一次已记录到访时间及关键未知信息。没有路线数据时只显示直线距离，不写成步行时间；营业状态未知时标注待确认。

### 6.2 生成顺序

1. 从常去店、收藏与授权地点数据中生成候选池。

2. 排除不再推荐、确认停业及与用户硬限制明确冲突的候选。

3. 结合预算和距离排序；资料缺失应降低优先级并标注，不默认符合。

4. 根据最近已记录餐食降低重复店铺、菜系与主要食材的权重。

5. 加入有限的尝鲜候选，再生成最多三个有差异的选项。

6. 输出基于已知事实的解释，不让语言模型自行创造店铺事实。

首版使用可配置规则即可。建议先保证候选可达与约束匹配，再考虑喜欢程度、减少重复、菜式多样性和尝鲜。最近吃过是软惩罚，不是绝对禁用；用户可主动选择熟悉的店。

营养因素优先作用于点餐方向。仅凭餐馆标签不能断言这一餐的营养构成，也不能把“轻食店”直接等同于低热量或均衡。

### 6.3 推荐不足与反馈

候选不足时解释原因，允许用户主动扩大距离或预算；没有明确选择前，不静默放宽硬限制。过敏相关信息不全的候选不能以“已符合过敏限制”身份展示。

换一组时，候选充足则避免重复本会话已展示的店；不足时说明已展示全部符合条件的候选。“帮我选”仅从当前合格候选中选择，并保留撤回和查看其余选项的入口。

反馈包括喜欢、不喜欢、今天不想吃、太远、太贵、吃过太多次、已关门。暂时拒绝不能自动转成永久黑名单。

### 6.4 餐馆信息

店铺至少包含名称、区域或地址、来源、创建或更新时间；价格、营业时间与菜单允许为空。连锁分店按具体地址区分，私人昵称关联具体店铺而不直接覆盖公共名称。

试点可人工维护少量办公区餐馆。第三方地点服务的覆盖、授权、费用和字段可用性在选型时验证；首版不依赖未经确认的大众点评、美团接口或未经授权的抓取。

## 7 饮食记录与 AI 识别

### 7.1 最小记录

用户可以只输入“今天午饭吃了某家店”，也可拍照后补充信息。保存至少需要餐食描述或餐馆之一；照片、份量、价格、同行人和评价均可选。餐次与就餐日期提供默认值并允许修改。

记录状态区分“计划去”“确认吃过”“已取消”；只有确认吃过才进入饮食历史与重复惩罚。点击导航不能自动视为实际用餐。

支持补记、编辑、删除、复制常吃餐食与多个餐次。多人共餐可以共享餐馆和菜名候选，但每个人必须确认自己的实际食物及份量；不得把整桌照片平均分给每个人。

### 7.2 照片识别流程

照片上传后，AI 返回可能的菜名、主要食材、烹饪方式与不确定项。用户可快速确认、修改或跳过识别；未经确认的内容以 AI 草稿保留，不当作确定事实参与强结论。

首版先覆盖单人份常见套餐和简单菜式。火锅、混合大锅菜、多盘合餐、遮挡严重或非食物图片进入低可信路径，允许人工补充，不强行生成完整营养表。

AI 任务异步执行。超时后记录仍可保存，状态显示分析中或分析失败，并提供重试；用户已手动修改的字段不被迟到的模型结果覆盖。删除记录后，未完成任务的回调不得恢复记录。

### 7.3 减少记录负担

从今日选中的餐馆自动带入店名；常吃菜一键复用；份量默认可跳过。饭后提醒默认关闭，用户主动开启后，每个餐次最多提醒一次，并可直接关闭。没有打卡的日期不触发惩罚式提示。

## 8 营养反馈的能力边界

二维照片中的份量估计存在固有限制，相关研究仍将其作为需要解决的核心问题。因此，产品应把照片识别作为食物候选输入，将营养结果定义为有依据、可纠正的估算，而不是测量结果。[图像份量估计研究](https://arxiv.org/abs/2404.12257)

### 8.1 首版展示内容

| 内容 | 展示条件 | 不满足条件时 |
| - | - | - |
| 菜品与食物类别 | AI 候选经确认或用户填写 | 提示补充，不默认识别正确 |
| 热量区间 | 食物匹配、份量假设与估算依据可追溯 | 显示暂无法估算 |
| 蛋白质 脂肪 碳水 | 具备食物数据和可用份量信息 | 隐藏缺失项，不显示为零 |
| 食物类别回顾 | 已确认的蔬菜、主食、肉蛋豆等标签 | 只统计有标签的记录 |
| 维生素 矿物质 | 后续有配方、份量与相应数据库支持 | 首版不承诺定量展示 |

营养估算链路为“确认食物 → 匹配食物或配方数据 → 确认或说明份量假设 → 计算并展示区间”。数据库存在不同来源与性质的数据，例如分析值、标签值及膳食调查食品数据，需保留来源和适用范围。[USDA 数据说明](https://fdc.nal.usda.gov/data-documentation/)

中国餐饮的数据库覆盖和商业授权仍需单独验证。没有匹配记录时不能让模型编造每 100 克营养数值；用相近菜式代替时应明确标注。

区间须来自可追溯的份量或配方假设，不任意给所有识别结果套用同一个百分比。未经校准，不使用“95% 置信区间”或虚假的高精度可信度分数。

### 8.2 历史解释与文案

回顾基于最近七天的已记录餐食，同时显示记录了几天、几餐和哪些餐次。数据少时降低个性化程度，不推断未记录餐次，不把午餐记录当作全天摄入。

可以说：“最近记录的三顿午餐中，两顿是面食，今天可以换个方向。”有蔬菜标签时可以统计“含蔬菜的记录次数”；没有识别到蔬菜不能直接写成“你没吃蔬菜”。

不能说：“你缺乏维生素 C”“今天摄入不足”或“这份菜绝对没有过敏原”。过敏原可能存在于酱料、配料或共用加工环节，APP 不提供安全认证，相关用户需自行向餐馆确认。

首版不默认计算个人每日热量目标，不评价用户自律程度，也不因记录不完整生成健康总分。

## 9 同事一起吃的轻量协作

P0 采用临时午饭邀请，无需建立复杂好友关系。发起人设置区域、预算和截止时间，分享链接；参与者以昵称及临时会话参与，是否采用 H5 承载由客户端方案决定，目标是不强制所有人安装 APP。

每人提交本次硬限制与可接受条件后，系统筛选共同候选。个人饮食历史不分享给其他成员；初版群体推荐主要使用本次共同约束，不汇总私人营养信息。

发起人发布最多三个候选。参与者可选一个或多个能接受的选项，也可选“都不合适”并说明原因。投票是偏好表达，不应覆盖已经登记的硬限制。

按支持人数建议结果，平票时由发起人确认，或在明确操作后随机选择。未投票表示未表态，不计为赞成。

无共同可接受选项时，显示冲突并允许成员调整本次条件或拆分就餐；不自动放宽过敏限制。若发布后候选或硬限制变化，需要生成新一轮并重新确认，旧票不悄悄沿用。

建议邀请在当日结束后过期；在候选仍有效且邀请未关闭时可提前结束。过期链接只能查看必要结果或提示结束，不能继续改票。匿名访问需使用不可预测的邀请令牌；票数仅适合熟人协调，不承担高可信身份认证。

## 10 数据与实现约束

以下为支持产品行为的逻辑实体，供后续技术设计使用，不限定数据库或微服务架构。

| 实体 | 关键内容 |
| - | - |
| 用户偏好 | 预算 距离 食物限制 收藏 黑名单 通知设置 |
| 餐馆 | 分店标识 名称 地址 来源 更新时间 可选菜单与价格 |
| 餐食记录 | 用户 日期时区 餐次 状态 餐馆 图片 描述 版本 |
| 食物条目 | 菜名 食材标签 份量 来源 用户确认状态 |
| 营养估算 | 输入版本 数据来源 假设 各指标范围 模型或规则版本 |
| 推荐会话 | 本次约束 候选 解释 展示顺序 用户选择 策略版本 |
| 午饭邀请 | 令牌 参与者 截止时间 候选版本 投票 最终结果 |
| 用户反馈 | 目标对象 原因 临时或长期 生效期限 |

MVP 可采用一个后端应用加数据库、对象存储和异步任务，不预先拆成大量微服务。模型调用、地图调用和营养计算使用独立模块，便于替换。

规则负责过滤与排序，AI 负责识别和自然语言表达。业务接口必须校验模型输出结构；菜单文字或图片里的指令不能改变权限、数据范围或推荐约束。

保存餐食、投票和最终确认须处理重复提交。用户纠正、删除或补记后，相关统计与后续推荐须更新；修改后的输入产生新估算版本，旧结果不能覆盖新版本。

外部服务故障不阻断手动记录和已有餐馆推荐。重复图片优先在同一用户范围内复用结果，缓存键包含输入与模型版本，不借缓存暴露其他用户图片。

## 11 隐私与体验要求

饮食记录、照片、精确位置及健康相关限制默认私有。邀请只暴露完成决策必需的信息，不展示个人完整记录、热量、私人地址或过敏病史；群体冲突可用不指向个人的方式说明。

按功能请求相机、照片、定位、通知权限，拒绝后给出手动路径。首版不需要后台持续定位；常用区域可手动设置。上传照片移除无关定位元数据，使用受访问控制的存储，日志不记录图片内容、精确坐标或健康备注。

用户可删除单餐和注销账户。上线前明确在线数据、图片、缓存、异步任务、备份及第三方处理的删除范围与时限，并在相应流程验收，不能只删数据库主记录。

调用外部 AI 前明确数据用途与处理方，不默认将用户照片用于模型训练。公开照片墙与商家可见的用户饮食档案不属于首版。

大陆公开发行时，产品上线清单需单独核实主体、APP 备案、隐私政策、SDK 数据处理、应用商店和地图数据使用要求；本 PRD 不把任何具体审批结论作为既定事实。

以下性能值为验收目标，需在声明的设备、网络、数据规模下测试：

- 自有餐馆池推荐 P95 不超过 2 秒；外部服务慢时先返回已有可用候选。

- 手动保存 P95 不超过 1 秒，不等待图片识别完成。

- 图片识别在 15 秒未完成时转为后台状态，不让用户一直停在等待页。

- 常见单人餐记录的用户操作时间中位数不超过 30 秒；这一指标不包含等待 AI 的时间，等待时间另报。

- 字体可读、按钮可触达；失败时保留已填写内容，弱网下提供草稿与重试。

## 12 验收标准与必要测试

| 编号 | 场景 | 通过标准 |
| - | - | - |
| A01 | 拒绝定位与相册权限 | 仍可手动选区域、添加店铺、记录餐食 |
| A02 | 新用户没有历史 | 能用已有餐馆得到推荐，不要求先连续打卡 |
| A03 | 只有一个合格候选 | 只展示一个并说明，不补虚构店铺 |
| A04 | 预算与食物限制冲突 | 不悄悄放宽限制，用户可主动调整或结束 |
| A05 | 选择餐馆后未实际就餐 | 不进入已吃历史，不影响营养统计 |
| A06 | 最近重复就餐 | 在其他条件接近时降低重复候选优先级，并给出可追溯原因 |
| A07 | 模糊或非食物照片 | 允许保存和人工填写，不生成确定营养结论 |
| A08 | AI 失败或超时 | 记录不丢失，重试不重复生成餐食 |
| A09 | 用户修改后旧任务返回 | 旧结果不能覆盖新内容或删除状态 |
| A10 | 只记录午餐 | 回顾明确午餐覆盖，不生成全天摄入结论 |
| A11 | 缺少营养数据 | 显示未知或隐藏，不写零、不编造维生素值 |
| A12 | 合餐照片 | 每人可确认自己吃的部分，不自动平均整桌热量 |
| A13 | 投票平票或无人投票 | 不伪造共识，由发起人确认或重新选择 |
| A14 | 投票后变更硬限制 | 重算候选并开启新一轮，不沿用失效投票 |
| A15 | 越权访问或过期邀请 | 拒绝读取私人记录及修改投票 |
| A16 | 删除餐食与账户 | 按已确定的数据生命周期删除，并阻止任务回写 |

必要测试包括推荐规则单元测试、记录与任务状态集成测试、多人并发投票与重复提交测试、访问控制测试、弱网和外部服务失败测试，以及上述完整用户路径的端到端测试。

AI 验证集须使用经授权的目标餐饮照片，覆盖单人套餐、混合菜、合餐和非食物图片；分别评价菜名候选、用户纠正成本及是否正确拒绝不确定输入。营养误差验证需要具备可核对食物、配方和份量的数据，不能用模型自己生成的数值作为真值。没有这类基准前不发布准确率承诺。

本节是测试计划与验收要求，不代表已经实现或通过测试。

## 13 指标与试点验证

北极星指标建议采用“每周确认采纳推荐的就餐次数”：用户选中推荐后，又确认实际吃过，按用户和餐次去重。它比推荐点击量更接近实际价值，但仍是用户自报，不能当作支付或到店验证。

| 指标 | 口径 | 初始观察目标 |
| - | - | - |
| 决策耗时 | 从查看候选到确认最终餐馆；同时报告未完成率 | 中位数相对原有方式下降 30% |
| 推荐确认就餐率 | 已确认实际就餐的推荐会话数 ÷ 当日全部有效推荐会话数 | 首期争取达到 30% |
| 午餐记录覆盖 | 每位用户实际记录的工作日午餐数 ÷ 试点工作日数 | 典型用户每周至少三餐 |
| 次周核心留存 | 首周完成选餐或记录的新用户中 次周再次完成核心行为的人数占比 | 试点观察 30% 以上 |
| 无结果率 | 无合格具体餐馆的会话数 ÷ 推荐会话数 | 按原因记录并优先修复 |
| AI 纠正负担 | 有识别结果的记录中 需改关键菜名或食材的比例与操作时间 | 首轮建立基线 |
| 单次成本 | AI 地图 存储等可变成本 ÷ 成功确认的核心行为次数 | 建立实际基线后定预算 |

以上目标是试点讨论阈值，不是行业基准。未完成、无候选与没有餐后反馈的会话不能从漏斗中消失；用户主动开启和日程自然差异应单独观察。

建议邀请一个办公片区的 20 至 30 名用户，持续两周。先记录原有选餐方式的耗时，再比较常去店随机选择与基于近期记录的推荐。小样本用于发现流程问题和方向性信号，不声称统计显著。

首轮验证三个问题：推荐是否真的省时间；用户是否愿意持续记录；同事投票是否缩短讨论而非增加步骤。若投票增加负担，可先简化为一人选择后分享结果；若 AI 没有降低输入成本，保留手动记录并推迟复杂识别。

建议事件包括 recommendation_requested、recommendation_shown、candidate_selected、decision_confirmed、meal_saved、meal_confirmed、meal_corrected、vote_submitted 和 no_candidate。事件关联会话与候选版本，不在埋点中上传餐食原文、图片或健康备注。

## 14 分阶段交付与商业路径

### 14.1 按验证结果推进

| 阶段 | 交付内容 | 进入下一阶段的条件 |
| - | - | - |
| 概念验证 | 访谈、纸面或可点击流程、人工餐馆池、原有决策基线 | 能确认高频需求与可行记录负担 |
| MVP 核心 | 推荐、手动记录、历史、轻量投票、可降级的照片识别 | 核心验收通过且试点有人持续使用 |
| 体验优化 | 纠错便利性、点餐建议、地图接入、营养估算覆盖 | 采纳和留存改善，单次成本可接受 |
| 小范围商业试验 | 商家认领、菜单更新、合作导流 | 特定片区有稳定用户与可归因需求 |
| 规模扩展 | 更多区域和合作形式 | 用户体验、商家供给与运营能力均支持 |

具体开发周期、费用、端的选择和人员安排需在技术方案、数据供应商与团队投入明确后估算，不将上述阶段直接换算为承诺日期。

### 14.2 商家侧的合理切入口

商家入驻优先解决资料真实性：认领店铺、更新营业时间、菜单、价格及菜品信息。随后再试验午间套餐或合作导流，不在尚未形成稳定需求前搭建完整交易平台。

商家提供的营养信息需标注来源，不能直接称为已验证。赞助内容明确标识，仍遵守用户硬限制；付费不能覆盖过敏限制或伪装成个人饮食分析结论。

若考虑向大众点评、美团等方向扩展，应分开看待“合作导流”“商家工具”“评价社区”和“交易履约”。每条路径都需要额外供给、运营和治理能力，不能把用户增长简单等同于自动具备交易平台能力。

收入模式可以验证合作导流、商家资料与菜单管理服务，或面向个人的高级回顾能力。初期先测持续使用和付费意愿，不预设广告或订阅一定成立。

## 15 关键风险与待确认决策

| 风险 | 早期信号 | 对应措施 |
| - | - | - |
| 推荐只是随机换店 | 用户每次都换一组或回到固定店 | 与随机基线比较，改进候选质量 |
| 打卡成本过高 | 首餐之后很少再记录 | 减少必填项、复用常吃记录、允许无图 |
| 周边供给太少 | 多次推荐仍只有同几家 | 明示范围并允许用户扩大区域 |
| AI 错误损害信任 | 菜名和份量需要频繁纠正 | 缩小支持菜式，保留不确定状态 |
| 营养信息制造误导 | 午餐被解释成全天或输出确定缺乏 | 限制结论模板与数据覆盖条件 |
| 多人协作增加麻烦 | 邀请无人回应或讨论更久 | 简化交互，保留个人直接决定 |
| 商业推荐侵蚀体验 | 合作店不符合实际偏好 | 明示赞助并保持硬限制独立 |

开发前需确认五项决策：

1. 先验证选餐效率，还是把营养管理作为同等核心目标。当前建议优先选餐效率。

2. 首发客户端采用 iOS、Android、小程序或组合。用户端与投票链接的承载方式需一起决定。

3. 是否愿意先围绕一个办公区维护少量真实餐馆，或必须首日支持多个城市。

4. 是否将轻量多人投票纳入 MVP。当前建议保留，以覆盖原始同事场景，但避免建立社交系统。

5. 开发与运营投入、AI 月度预算和首批试点用户从哪里获得。

建议先验证这样一个具体结果：在熟悉的办公区域，用户打开 APP 后能更快选定一顿愿意吃的午饭，饭后愿意花很少时间留下记录，并在下一次推荐中看到记录带来的变化。
